# Кандидатогенерация услуг Авито

Для каждого из 2 452 поисковых запросов бенчмарка решение отбирает из корпуса 189 212 объявлений 50 кандидатов так, чтобы в них попали объявления, которые пользователь в итоге выбрал. Метрика — Recall@50.

**Итоговый ответ:** [`answer.csv`](answer.csv), **Recall@50 = 0.897905** на проверке платформы.

## Быстрый старт

Точное воспроизведение отправленного `answer.csv` занимает ~10 секунд. GPU и исходные данные не нужны:

```bash
python3.12 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python reproduce_answer.py      # -> output/answer.csv, побайтно равен answer.csv (проверяется SHA-256)
```

Полный пересчёт с нуля — индексы, эмбеддинги, симуляции, дообучение, обучение моделей. Около 6–7 часов на ноутбуке с 8 ГБ ОЗУ:

```bash
python prepare_data.py          # собирает data/*.parquet из частей в dataset/ и сверяет SHA-256
bash v4/run_final.sh            # -> output/answer_full_run.csv и сверка с answer.csv
```

## Подход в двух словах

1. **Кандидаты.** Для каждого запроса объединяются несколько независимых каналов поиска: лексический (BM25), нечёткий (символьные n-граммы), семантический (эмбеддинги), история похожих запросов, подкатегории, «перевод» слов запроса в слова объявлений, каналы с мягкой географией. Получается в среднем ~540 кандидатов, их полнота на валидации ~98%.
2. **Ранжирование.** CatBoost оценивает вероятность выбора каждого кандидата по 61 признаку. Итог — среднее вероятностей четырёх моделей, обученных на разных симуляциях. В ответ идут 50 лучших.
3. **Обучающие данные.** Ранжировщик обучается не на случайном отрезке train, а на **симуляциях бенчмарка из train**. Часть поисков объявляется «будущим периодом», и его объявления образуют корпус симуляции. Почему это ключевой момент — в разделе об ошибках.

## Данные и признаки

**Использованные данные:** `train.parquet` (пары «запрос → выбранное объявление») как история поведения и материал для симуляций; корпус `benchmark_items.parquet`; поля запросов бенчмарка как входы модели. Разметка бенчмарка не используется — её нет.

| Группа признаков | Что это | Зачем |
| --- | --- | --- |
| Лексика | BM25 по заголовку, по «заголовок + параметры + описание» и по параметрам; TF-IDF символьных 3–5-грамм заголовка; русский стемминг Snowball | Основной сигнал релевантности; n-граммы устойчивы к опечаткам и словоформам |
| Семантика | Косинус эмбеддингов `multilingual-e5-small`: исходной модели и дообученной на парах «запрос → выбранное объявление» | Синонимы и перефразы: «выложить плитку» → «ремонт ванной» |
| Модель «перевода» | Связи «слово запроса → слово объявления», выученные на истории: P(v\|w)·log lift | «вытяжка» → «вентиляция», «массовка» → «актёрское портфолио» |
| История | Распределение подкатегорий и выбранных объявлений у 35 ближайших прошлых запросов; точное совпадение текста; популярность | Перенос знаний с похожих формулировок |
| География | Та же локация, частота переходов «локация поиска → локация объявления», расстояние; центр для региональных локаций | Услуги локальны, но жёсткий фильтр по городу терял цели |
| Удалённые услуги | Доля выборов вне города для похожих запросов и для подкатегории; пометки «онлайн», «по всей России» | 60% промахов — объявления из другого города (онлайн-репетиторы, юристы) |
| Фильтры поиска | Выполнены ли пары «ключ значение» фильтра («Вид услуги …», «Тип услуги …», рейтинг) в параметрах объявления | Выбранное объявление соответствует фильтру в 95% случаев, случайный кандидат — в 54% |
| Относительные | Ранги кандидата внутри пула по каждому сигналу, доли от максимума | Деревья не сравнивают кандидатов одного запроса между собой — ранги дают это явно |

Всего 61 признак: 53 базовых (`v3/solution.py`), 5 признаков дообученного энкодера (`v4/ft_features.py`) и 3 признака фильтров (`v4/filter_features.py`).

**Правило категории.** При поиске внутри «Услуг» (`search_category = 114`) объявления других категорий не выдаются: в train такой выбор встретился 15 раз из 497 635.

## Модели и алгоритмы

- **Отбор кандидатов:** объединение топов 9 каналов (`v3/solution.py`, класс `World`). BM25 реализован в проекте.
- **Эмбеддинги:** `intfloat/multilingual-e5-small`. Дообучение (`v4/finetune_e5.py`) — контрастивное (InfoNCE по пакету), на парах «текст запроса → карточка выбранного объявления». Словарь заморожен, используется gradient checkpointing.
- **Ранжировщик:** CatBoost, Logloss, глубина 8, 1000 деревьев. Четыре модели:

| Модель | Признаки | Обучена на |
| --- | --- | --- |
| v5 | 61 | симуляции разбиения 0 (PB-3, PB-4) |
| v6 | 56 (без энкодера) | три других разбиения (PB-4, PB-5, PB-6) |
| mix | 56 | смесь случайных разбиений и разбиений со сдвигом тем |
| dw | 56 | разбиения со сдвигом тем «лето → осень» (PB-8, PB-9) |

- **Итог:** среднее вероятностей четырёх моделей с весами 0.25 (`v4/predict_final.py`), затем 50 лучших.

## Как проверялось качество до отправки

1. **Симуляции бенчмарка из train** (`v4/solution.py`, стадия `pb`):
   - случайные 40% контекстов поиска становятся «будущим периодом», остальное — историей;
   - корпус симуляции — все объявления, выбранные в «будущем», около 161 тыс., сопоставимо с 189 тыс. реального корпуса;
   - у 60% объявлений корпуса прошлые выборы приписываются их «старой версии» — это моделирует оборот объявлений: в реальном корпусе лишь 9.6% объявлений встречались в train;
   - запросы берутся по одному на текст, со стратификацией «текст встречался в истории × заданы фильтры» под распределение бенчмарка;
   - строятся «миры со сдвигом тем»: контекст попадает в «будущее» с вероятностью w/(1.5+w), где w — похожесть текста на запросы бенчмарка (`v4/text_shift.py`, классификатор по эмбеддингам и TF-IDF, без разметки).
2. **Честный контроль:**
   - тексты запросов разбиты на 5 групп, и модели оцениваются на группе, которой не было в обучении;
   - финальные решения принимались на **независимых разбиениях**, не участвовавших в обучении ни одной сравниваемой модели (PB-7, PB-10), потому что оценка внутри того же разбиения оказалась оптимистичной.
3. **Калибровка прокси по реальным попыткам.** Мир со сдвигом тем упорядочивает все отправленные решения так же, как проверка платформы, со стабильным смещением около −4 п. п. Итоговые модели дают на нём Recall@50 ≈ 0.94–0.945.
4. **Формат:**
   - каждый ответ проходит строгую проверку по всем требованиям условия: заголовок, `query_id`, до 50 уникальных `item_id` из корпуса, строчные символы, без BOM и индекса (`v3/solution.py`, стадия `check`; `reproduce_answer.py`);
   - запись атомарная — через временный файл.

## Найденные ошибки и что с ними сделано

| Что обнаружено при анализе | Как проявлялось | Что сделано |
| --- | --- | --- |
| **Смещённая валидация.** Первая схема брала цели только из пар train, чьи объявления случайно есть в корпусе | Валидация обещала 0.926, проверка дала 0.850; модель переоценивала «знакомые» объявления: 32% топа при 15% среди кандидатов | Симуляции бенчмарка из train с естественными целями |
| **Сезонный сдвиг.** train — лето, бенчмарк — осень | Котлы и дымоходы ×4, репетиторы ×3, кондиционеры ×0.4 | Миры со сдвигом тем в обучении и контроле |
| **Плотность конкурентов.** Корпус — объявления того же периода, что и запросы | У реальных запросов в 1.85 раза больше сильных совпадений в своей локации, чем в первых симуляциях | Корпус симуляции — все выборы «будущего периода» |
| **Оборот объявлений** | История train есть лишь у 15% реальных кандидатов (в первых симуляциях — у 34%) | Переименование прошлых выборов части объявлений |
| **Подгонка под одну симуляцию** | Модель лучше всего на том разбиении, где обучалась | Оценка на независимых разбиениях; ансамбль моделей с разных разбиений (+0.2–0.3 п. п.) |
| **Нарушение фильтров** | 14% слотов ответа — объявления, не подходящие под фильтр запроса | Точные признаки соответствия фильтру |
| **Промахи по географии** | 60% потерянных целей — из другой локации | Признаки удалённых услуг, смягчённая география, центр региональных локаций |
| **Семантические промахи** | «сваебойная установка» не находит «забивку свай» | Модель «перевода», e5 и его дообучение |
| **Чужие категории** | Объявления не из услуг в ответах на поиск внутри «Услуг» | Правило категории |
| **Инженерные ошибки** | Устаревшие кэши и зависимость от порядка строк; нехватка памяти GPU на ноутбуке | Контрольные суммы кэшей и порядка запросов; `v4/tools/run_safe.sh` (лимит GPU-памяти, контроль свопа); gradient checkpointing |

**Проверено и не дало выигрыша** на независимых разбиениях:
- ансамбли одной модели с разными зёрнами, более длинное обучение;
- расширение пула каналом дообученного энкодера;
- сжатие дубликатов объявлений;
- топонимы из запроса против адреса исполнителя (`v4/topo_features.py`);
- объединение по рангам, логитам, RRF;
- функция потерь YetiRank (`v4/train_rank.py`).

**Оставшиеся ограничения.** Разрыв ~4 п. п. между симуляцией и проверкой одинаков для всех версий решения. Это выборы, слабо связанные с текстом запроса, и запросы без категории (9% бенчмарка), которых в train практически нет.

## Воспроизводимость

- `reproduce_answer.py` использует артефакты итогового прогона и воспроизводит **отправленный файл побайтно** на любой машине:
  - `artifacts/`: признаки кандидатов бенчмарка в исходной точности float32, 4 модели CatBoost, `MANIFEST.json` с SHA-256;
  - инференс CatBoost детерминирован, порядок суммирования и правило разрешения равенств фиксированы.
- `v4/run_final.sh` пересчитывает все артефакты из исходных данных, всё локально. Сеть нужна один раз — скачать открытые веса e5 с Hugging Face (ревизия зафиксирована). Дообучение и кодирование нейросети на GPU (Apple MPS или CUDA) дают микроскопические различия в числах с плавающей точкой на разном железе. Поэтому полный пересчёт на другой машине может отличаться от отправленного ответа в единичных позициях; сценарий в конце печатает долю совпадения.
- Правил под конкретные `query_id` нет: `query_id` используется только для порядка строк и записи ответа.
